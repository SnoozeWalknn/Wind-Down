# Wind Down — engineering and interaction specification

## Product
A compact native Windows 11 power timer. Only Shut Down (default) and Sleep. C# / WinUI 3, system theme and accent, Segoe UI Variable, semantic theme brushes, Mica backdrop, native caption controls. Dark appearance uses the Midnight palette: a deep navy window layer, blue-black cards, restrained blue-gray strokes, and cool high-contrast text while keeping the Windows accent color. Light appearance continues to use Windows resources; System selects Light or Midnight from the current Windows app theme. A 480-DIP window with a single focused task, 32-DIP content margins, 8-DIP spacing rhythm, 6–12-DIP corners, quiet separators, and a generous typographic time picker. No web surface.

The application identity uses a custom crescent-moon icon with transparent rounded corners and embedded 16, 20, 24, 32, 40, 48, 64, 128, and 256-pixel frames. The vector master and deterministic icon generator are retained in the development deliverable; only the compiled ICO ships to end users.

## States and transitions
Loading → Ready or Active after querying Windows. Ready → Registering → Active only after registration and read-back succeed. Errors return to the prior authoritative state with an inline explanation. Active → Cancelling → Ready only after task deletion is verified. Active → Editing keeps the existing schedule armed until a replacement commits atomically. Back returns to Active. Active → Requesting at the deadline; receipts distinguish request accepted, missed, and failed. Never infer actual power-off from API acceptance. A schedule identity accompanies all cancellation and notification actions; stale notifications cannot cancel a replacement.

## Scheduling authority
Windows Task Scheduler is the durable rendezvous for both actions, independent of UI lifetime. It is not a common power-command abstraction: shutdown uses InitiateShutdownW(POWEROFF, zero grace, no FORCE flags); sleep uses SetSuspendState(false, false, false). A small WinExe worker has no console or UI framework dependency. Both APIs require enabling the current user's existing shutdown privilege; no UAC request, credential storage, service, or highest-privilege task.

One per-user action task contains the entire schedule in its registration metadata (version, GUID, action, UTC deadline, creation time, boot identity, warning choice). Registration uses CREATE_OR_UPDATE and read-back. A per-user named mutex serializes worker execution, cancellation, and replacement. Worker rereads authoritative metadata and validates identity, boot session, deadline, and lateness, then commits and verifies a Requesting receipt in the Windows task metadata while disabling future triggers. This durable claim is the execution linearization point; cancellation instead removes an unclaimed task under the same mutex. Once execution has claimed a schedule, cancellation reports that it is too late, never false success. The final execution result remains in task metadata, independently readable by the UI. Only preferences, a cancellation receipt, and a bounded last-error diagnostic live in LocalAppData. Completed tasks expire after 24 hours; they never rerun.

Version 1.0 uses the `WindDown-{user SID}` task family and `LocalAppData\Wind Down`. On first launch it moves the prior preference/result state, atomically re-registers a future active schedule under the Wind Down task identity with the new executable paths, verifies the replacement, and only then removes the legacy action and warning tasks. Completed and diagnostic legacy tasks are removed. The installer also removes obsolete shortcuts, protocol registration, and inactive installation files.

A separate warning task launches the app invisibly to issue an actionable native notification. A warning-only new instance exits after submitting the notification; a running visible/tray instance receives the request through a per-user named pipe. Failure to create a requested warning rolls back the new schedule before reporting failure. Notification presentation remains best effort because Windows notification settings and Do Not Disturb are outside app control. GUID-bound Cancel activates the existing app or launches it. Tray double-click opens; context menu offers Open, Cancel, and Exit. Close hides while active; explicit Exit leaves Windows-owned scheduling in place.

## Time policy and edge cases
Duration: 0–24 hours and 0–59 minutes, with minutes fixed at 00 when hours is 24 and a minimum of one minute. Clock: Windows regional format, next future occurrence, explicitly labeled Today/Tomorrow/date. Invalid DST gap times are rejected with an explanation; repeated DST times select the next future occurrence. Resolve once into an absolute UTC instant; later timezone changes affect display, not the chosen instant. Countdown is max(0, deadline − UtcNow), never decremented UI state.

Schedules do not wake the PC, do not run after sign-out, and are skipped after a Windows restart. No delayed catch-up after sleep: tasks use StartWhenAvailable=false, WakeToRun=false, battery execution allowed, and a one-minute late-execution guard. This deliberately avoids a surprise shutdown on resume. If Windows delays execution by more than a minute, the worker records a missed result. Existing future schedules remain valid across ordinary sleep/wake in the same boot. A boot-session GUID is read through SystemBootEnvironmentInformation, immune to wall-clock adjustments.

Task Scheduler access/policy failures remain visible and never become an active countdown. External task removal is detected by polling; an unrecognized task is never overwritten. Power API failures persist a task-owned result for reopening. A crash after the durable claim leaves Requesting, which is displayed as a request started with no automatic retry. A final receipt-write failure is not mislabeled as a failed power API call. Task metadata and worker arguments must agree; executable location must exist before scheduling. A move/uninstall must cancel schedules first. Protect unsaved work: no /f, no forced session termination; Windows or another app can block shutdown, so success is described as request accepted.

## Interaction system
In / At segmented mode controls. Hours and Minutes are typographic editable dials: adjacent faded values, accented selected value, direct typing, Up/Down, wheel accumulation, touch swipe, Tab, and Enter. Values wrap within their ranges on stepping; invalid typed values remain visibly invalid rather than silently scheduling a different time. Presets 30 min, 1 hr, 2 hr, 3 hr. Enter commits a dial; the primary button schedules. Accessible names, help text, native edit/selection semantics, system focus visuals; no per-second screen reader announcements. Active state prioritizes action status, a stable tabular countdown, local target date, and a full-width Cancel action.

## Validation
Pure time-policy tests cover zero, minute bounds, >12 hours, midnight, 12/24-hour conversion, DST gaps/folds and absolute countdown. Real Task Scheduler integration tests exercise registration/read-back/replacement/stale cancellation/worker execution/failure receipts with an inert test executor and isolated task names. No test invokes real power APIs. Build self-contained x64 release, launch native app, inspect both themes and active/error states, exercise keyboard/direct edit/presets/cancel/close/relaunch/tray. Real shutdown and physical sleep require a separate user-controlled acceptance test after saving work.
